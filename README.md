# Beyond Accuracy: Review-Capacity-Aware Mobile-Money Fraud Detection

This research project asks a practical question:

> If a mobile-money fraud team can review only a limited number of alerts, how
> should transactions be prioritised to catch as much fraud as possible without
> overwhelming investigators or inconveniencing genuine customers?

The project uses the public **PaySim synthetic dataset** and compares:

1. PaySim's existing `isFlaggedFraud` rule as a separate baseline;
2. logistic regression as an interpretable CPU baseline; and
3. XGBoost as a stronger task-specific model.

The dashboard translates scores into operational outcomes: alerts per 10,000
transactions, fraud caught, fraud missed, and genuine transactions incorrectly
sent for review.

> [!IMPORTANT]
> A high risk score is a **prediction, not proof of fraud**. This prototype
> prioritises synthetic transactions for human review. It does not block real
> payments and has not been tested on customer or Tanzanian mobile-money data.

## Project status

The reproducible baseline and dashboard are implemented and tested locally. The
repository contains no invented results. The table below records the measured
500,000-row baseline run from 18 November 2026; generated artifacts remain local
under the Git-ignored `results/latest/` and `artifacts/latest/` folders.

NVIDIA Kumo Tabular remains a later optional comparison. The existing scripts
under `scripts/` are local feasibility checks, not final fraud results.

### Measured baseline result

The models used the same naturally sampled 500,000 training transactions. The
validation and test partitions retained their natural fraud rates. The review
threshold was selected on validation data for 100 alerts per 10,000; it was not
retuned on the test period.

| Test metric | Logistic regression | XGBoost | Existing rule |
|---|---:|---:|---:|
| Average precision | 0.2794 | 0.3603 | 0.0195 |
| Precision | 32.48% | 35.53% | 100.00% |
| Recall | 35.30% | 40.02% | 0.56% |
| Fraud caught | 442 | 501 | 7 |
| False positives | 919 | 909 | 0 |
| Missed fraud | 810 | 751 | 1,245 |
| Test alerts per 10,000 | 152.12 | 157.60 | 0.78 |

The test period contained 89,466 transactions, including 1,252 synthetic fraud
labels. XGBoost ranked fraud better than logistic regression in this run, while
the existing rule produced no false positives but missed nearly all fraud. A
particularly useful finding is **review-workload drift**: thresholds chosen for
100 validation alerts per 10,000 produced about 152–158 alerts per 10,000 in the
later test period. Review capacity therefore needs temporal monitoring rather
than a one-time threshold choice.

Total local experiment runtime was 3.77 seconds after installation and peak
process memory was 590.7 MiB on the stated Mac. These are one sampled synthetic
baseline, not evidence of production performance.

## Why this project is different

Fraud is rare, so a classifier can appear accurate while missing the cases that
matter. A model can also achieve high recall by creating an unusably large
review queue. This project therefore makes investigator capacity a first-class
constraint.

The final threshold is chosen on validation data for a declared review budget,
such as 100 alerts per 10,000 transactions. The latest test period is opened
only after preprocessing, models and thresholds are fixed. Dashboard threshold
changes are clearly labelled exploratory and do not replace the final result.

## Dataset

- **Source:** [PaySim on Kaggle](https://www.kaggle.com/datasets/ealaxi/paysim1)
- **Publisher:** Edgar Alonso Lopez-Rojas
- **Licence:** CC BY-SA 4.0, as listed for the canonical Kaggle dataset
- **Size:** 6,362,620 synthetic transactions; this file contains 743 distinct
  hourly steps numbered 1–743
- **Target:** `isFraud`
- **Types:** `CASH_IN`, `CASH_OUT`, `DEBIT`, `PAYMENT`, `TRANSFER`

PaySim was generated by a simulator informed by aggregated mobile-money logs.
The records are synthetic. This repository must never contain employer or real
customer records.

Please cite:

> E. A. Lopez-Rojas, A. Elmir, and S. Axelsson. “PaySim: A Financial Mobile
> Money Simulator for Fraud Detection.” 28th European Modeling and Simulation
> Symposium, 2016.

## Leakage and feature policy

The models use transaction `type`, `amount`, `log1p(amount)`, hour-of-day and
elapsed simulation day. The following are excluded from model inputs:

- `oldbalanceOrg`, `newbalanceOrig`, `oldbalanceDest`, `newbalanceDest`
- `nameOrig`, `nameDest`
- `isFlaggedFraud`

The publisher warns against using the four balance columns for fraud detection
because fraud transactions are cancelled, allowing those balances to leak the
outcome. Account IDs are omitted from the initial baseline. `isFlaggedFraud` is
an existing rule, so it is evaluated separately rather than used as a feature.

## Fair evaluation design

- Split chronologically by **complete time steps**, never randomly across time.
- Earliest 70% of steps: training.
- Next 15%: validation and threshold selection.
- Latest 15%: untouched final test.
- Fit preprocessing only on the training sample.
- Give both models the same training examples and features.
- Preserve the natural fraud rate in validation and test data.
- Disclose any training cap; do not fraud-enrich the default training sample.
- Select the final threshold on validation data for the review budget.
- Report precision, recall, average precision, false positives, missed fraud,
  confusion matrix, runtime and memory—not accuracy alone.

```bash

```

Tests verify that time partitions do not overlap, forbidden columns cannot
enter the feature frame, training sampling is repeatable, the review capacity
is respected and confusion-matrix counts are correct.

## Run the first experiment

The default caps training at 500,000 naturally sampled rows. Validation and test
retain their natural class distribution and are not fraud-enriched.

```bash
source .venv/bin/activate
/usr/bin/time -l python train.py \
  --csv PS_20174392719_1491204439457_log.csv \
  --max-train-rows 500000 \
  --review-budget-per-10000 100
```

For a faster smoke run before a demonstration:

```bash
python train.py \
  --max-train-rows 100000 \
  --xgb-estimators 100 \
  --review-budget-per-10000 100
```

Outputs:

- `results/latest/metrics.json` — metrics, splits and disclosures;
- `results/latest/test_predictions.csv.gz` — scored test transactions;
- `results/latest/validation_capacity_curve.csv` — validation trade-offs;
- `artifacts/latest/*.joblib` — preprocessing and model artifacts.

Do not present a smoke run as a full-scale result. The report records whether
training was sampled.

## Limitations

- PaySim is synthetic and models only selected fraud behaviours.
- Performance does not establish effectiveness on Tanzanian transactions.
- Demographic fairness cannot be assessed because relevant attributes are absent.
- Operational fraud costs and investigator capacity are not supplied by PaySim.
- Features intentionally omit customer history and network relationships.
- Model probabilities are not evidence and may not be calibrated.

## Next research steps

1. Add rolling temporal backtests to measure stability.
2. Add non-identifying historical velocity features using past events only.
3. Study probability calibration and cost-sensitive threshold policies.
4. Compare Kumo Tabular with XGBoost on matched historical examples if local
   compatibility or NVIDIA API access becomes available.
5. Validate the design on another public synthetic dataset before considering
   any governed real-world research.
